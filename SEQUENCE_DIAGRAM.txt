  NESTJS MICROSERVICES TEMPLATE -- SEQUENCE DIAGRAMS
================================================================================

  Companion to SYSTEM_DIAGRAM.txt, which shows the static structure. This
  file shows the five flows that matter most, in call order.

  Reading the notation:

      A |---- message ---->| B      A calls B
      A |<--- response ----| B      B answers A
        | (something)      |        internal work on that participant's
        |                  |        own lifeline -- no network hop

  View in a fixed-width font.

  Contents:
      1. demo-ui login
      2. admin-ui login
      3. Editing an item
      4. Deactivating a user
      5. Logging out

================================================================================
  WHY THESE FIVE
================================================================================

  1 vs 2  -- the same credentials, two deliberately different session
             models. demo-ui ends with the token in browser-reachable
             JavaScript; admin-ui ends with it encrypted in an httpOnly
             cookie the browser can send but never read. That single
             difference is the reason admin-ui needs Route Handlers at
             all.

  3       -- the only flow where one backend service calls another
             directly, bypassing the gateway. It is also the flow that
             makes role changes real: data-service does not trust the
             JWT's own "roles" claim, it asks auth-config, and
             auth-config answers from the database.

             With AUTH_MODE=mock this entire validation hop is skipped
             and every caller is treated as one hardcoded user -- which
             makes any permission test meaningless. Use AUTH_MODE=remote
             when testing permissions.

  4 and 5 -- both work by bumping tokenVersion, which is what makes
             revocation immediate rather than "eventually, once the
             15-minute access token expires." 4 is revocation done TO a
             user by an admin; 5 is a user revoking their own sessions.
             The audit log records the former.

================================================================================
  WHAT IS NOT DRAWN
================================================================================

  - Token refresh. admin-ui refreshes server-side inside its upstream
    helper: if a request 401s, it calls POST /auth/refresh once, retries
    the original request once, and gives up if that fails. It never
    retries more than once -- a refresh loop against a service that is
    down is worse than a clean failure.

  - proxy.ts. Every /admin/* page load in admin-ui passes through it
    first. It only checks that the session cookie exists and decrypts --
    it is a presence check, not an authorization check, and it cannot
    tell whether the session belongs to an admin. auth-config decides
    that on every single API call.

  - Error paths, beyond the 403/409 branches shown in flow 4. Upstream
    status codes and messages are passed through to the browser rather
    than being flattened into a generic failure.
